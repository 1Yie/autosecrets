# AutoSecrets Operations Console and Secure Management Workflows

Status: ready-for-agent

## Problem Statement

AutoSecrets currently exposes the first vertical slice through a minimal Web interface. Bootstrap, password login, Application and Environment creation, Secret authoring, Publish, Node Group membership, Assignment creation, Agent enrollment, and basic node status exist, but the interface presents them as loosely connected forms and raw tables. There is no dedicated authentication layout, no operational Overview, no durable navigation hierarchy, no Application or Managed Node workspace, and no reliable way to distinguish healthy, converging, failed, offline, or unconfigured state.

The current UI also exposes deeper product gaps. An Assignment is pinned to one Bundle Revision even though the domain says it relates a Secret Bundle to a Node Group. A Managed Node stores only one observed revision even though it can receive several Assignments. Existing Environment names do not encode a trustworthy protection level. High-risk actions lack Step-up Authentication and structured Operation Reasons. The current Audit Event shape is not suitable for filtering or investigation. Lists return unbounded arrays, and the Agent cannot yet execute the constrained service lifecycle required for safe Unassignment.

From an Administrator's perspective, the product still feels like an implementation scaffold rather than a professional operations console. Important state is difficult to scan, high-risk effects are not explained before submission, asynchronous Convergence can be mistaken for synchronous deployment success, and several workflows can be created but not safely reversed. Improving only colors and spacing would make these weaknesses less visible without making the system more trustworthy.

## Solution

Deliver a professional, Chinese-first AutoSecrets operations console backed by the domain, identity, audit, Convergence, and Agent capabilities required to make every visible state and action real. The console will use a dedicated authentication experience, a collapsible navigation shell, an operational Overview, deep-linked Application and Fleet workspaces, structured Audit Event investigation, responsive dense tables, complete light and dark themes, and consistent Watermelon UI-based controls.

The work will be delivered in four evidence-backed vertical slices rather than as a frontend-only rewrite:

1. Establish the design system, AutoSecrets identity, Organization-aware authentication, mandatory MFA, bounded Sessions, Step-up Authentication, Administrator and Viewer authorization, and the authenticated shell.
2. Rebuild the Application, Environment, Secret, Draft, Publish, Rollback, and Assignment-authoring experience while correcting Environment protection, Secret Value transport, and Assignment semantics.
3. Add per-Assignment Convergence, Managed Node and Node Group workspaces, cursor-based management lists, global search, the Overview projection, and structured Audit Event investigation.
4. Add constrained Activation Policies and persistent two-phase Unassignment, including cleanup failure, offline nodes, and explicit unconfirmed-cleanup handling.

The first post-login screen will answer “what needs attention now?” rather than present equal-weight summary cards. Every status will be derived by Core from explicit facts. Every Desired State change will have an Operation Reason and impact preview. Protected Environment and identity operations will enforce a server-side risk policy. Publish and Rollback will update Desired State, then expose independent Assignment Convergence without claiming global deployment atomicity.

## Implementation Decisions

- **Delivery shape**: Implement four vertical slices in order: Identity/Auth/Shell; Application and Secret workflows; Fleet/Convergence/Overview/Audit; Activation Policy and Unassignment. Each slice changes Core, PostgreSQL, Web, and Agent only where needed and must be independently deployable and testable.
- **Primary actors**: Administrator remains the primary operating role. Viewer is a real read-only role that can inspect all redacted metadata, Convergence, and Audit Events but cannot mutate Desired State, prepare Rotation, generate an Install Command, or perform Step-up actions.
- **Frontend architecture**: Use React function components and Hooks. Files use kebab-case; component identifiers use PascalCase; Hook files use kebab-case and identifiers use camelCase. Every props surface has an explicit interface. Components do not use `any`. Split components only for a clear responsibility, reusable behavior, complex state, or independent testing value.
- **Data ownership**: All management API reads and writes are wrapped by feature TanStack Query hooks. Components never call `fetch` or Axios directly. TanStack Query owns server state; Zustand owns shared cross-route client state; local React state owns transient presentation; React Hook Form and Zod own form state and validation.
- **Styling and components**: Tailwind CSS is the only styling system. Watermelon UI is the primary component and block registry. shadcn-derived primitives remain only where Watermelon has no equivalent. Domain-specific components compose those primitives; no second UI framework or duplicate primitive layer is introduced. Shared control geometry is defined at the primitive, not overridden at usage sites.
- **Design direction**: Build a professional operations console with graphite neutrals, restrained blue-green interactive emphasis, and independent semantic green, amber, and red. Avoid a one-hue palette, dominant purple, all-dark-blue security styling, gradients, glow, glassmorphism, oversized hero typography, decorative charts, card nesting, excessive rounding, and marketing composition.
- **Brand identity**: Replace the scaffold favicon as the product identity. Present three restrained geometric AutoSecrets mark directions based on controlled delivery, Convergence, or layered Secret state. Select one before finalizing full-color, monochrome, reversed, and small-size assets. The authentication visual uses real domain relationships but explicitly represents a product illustration, not live data.
- **Typography and icons**: Use a Chinese-capable, technical sans-serif hierarchy with stable sizes rather than viewport-scaled type. Letter spacing remains zero. Use the existing Lucide icon family for controls and navigation; unfamiliar icon-only actions have accessible names and tooltips.
- **Auth routing**: Add explicit authentication routes under a dedicated Auth layout for Bootstrap, login, MFA, member activation, Session renewal, and interrupted enrollment recovery. Protected routes redirect to login with a validated same-origin internal `returnTo`. Authenticated members visiting Auth routes return to the intended route or Overview.
- **Organization identity**: Bootstrap captures one Organization display name. Authentication and application shells show Organization name and hostname. The Organization display name can be changed by an Administrator through Organization management after Step-up Authentication and an Operation Reason.
- **Member schema**: Replace the Administrator-only identity assumption with Organization Members that have stable IDs, display snapshots, role (`administrator` or `viewer`), activation state, deactivation state, password credential, TOTP credential, Recovery Codes, invitations, Sessions, and Step-up Grants.
- **Bootstrap state machine**: Consuming the Bootstrap Code creates a pending first Administrator. That identity becomes active only after password setup, TOTP verification, Recovery Code generation, one-time display, and explicit confirmation. Interrupted enrollment resumes the same pending identity and never issues a normal Session early.
- **Member invitations**: Administrators create hash-stored, revocable, single-use Member Invitation Codes that expire after 24 hours. Codes are displayed once, pasted into a fixed activation route, never placed in URLs or browser storage, and never redisplayed. Replacement invalidates the old invitation.
- **Member lifecycle**: Members are deactivated, never physically deleted. Deactivation revokes Sessions, Step-up Grants, and unused invitations. Reactivation uses a new secure enrollment. Role changes and deactivation require Step-up Authentication, an Operation Reason, and Audit Events. A database transaction prevents removal or demotion of the last active Administrator.
- **Authentication policy**: Every active Organization Member uses password plus TOTP or one unused Recovery Code. Recovery Code use consumes the code. Regeneration invalidates the old set. Full MFA login and renewal issue a new Session and a five-minute Step-up Grant.
- **Password policy**: Accept 12–128 Unicode code points, permit passphrases, and do not require composition rules. Reject known breached/common passwords using an offline local check. Authentication failures use indistinguishable messages.
- **Abuse controls**: Apply server-side rate limiting and exponential backoff by account and source to login, TOTP, Recovery Code, invitation activation, and Step-up attempts. Do not permanently lock accounts. Anonymous invalid-session and CSRF attempts go to security logs; authenticated high-risk denials become Audit Events.
- **Session policy**: Sessions have a 12-hour absolute expiry and a 30-minute idle expiry. Only throttled, explicit member interactions update activity; polling and page visibility do not. Multiple tabs share recent interaction state, while Core remains authoritative. Renewal requires full MFA. Password changes require current password plus TOTP, revoke all Sessions and Grants, and issue one new Session for the current browser.
- **Break-glass recovery**: No anonymous Web recovery exists. A host-local Core command issues a short-lived, single-use recovery proof, revokes active Sessions, and forces new TOTP and Recovery Code enrollment. The recovery action is audited without exposing credential material.
- **Authorization UI**: Navigation omits modules wholly unavailable to the current role. Visible context actions that are restricted remain disabled with an explanation. Core authorization is the final boundary for every route and action.
- **Server-side risk policy**: Core centrally decides whether an action requires Step-up Authentication, object-name confirmation, an Operation Reason, and impact preview. The Web renders policy requirements; it does not reproduce authorization rules as the source of truth.
- **Step-up scope**: A five-minute Grant belongs to the current Session and is revoked with that Session. Install Command generation, member and role changes, Abandon Cleanup Confirmation, protection changes, and Protected Environment Publish, Rollback, prepare Rotation, Assignment, membership removal with Desired State impact, Activation Policy changes, and Unassignment require Step-up Authentication.
- **Operation Reasons**: Every Publish, Rollback, Assignment, Desired State-affecting membership change, Unassignment, cleanup abandonment, protection change, and identity high-risk action includes a stable category, a 10–500 character explanation, and an optional external reference. Initial categories are maintenance, incident response, access change, configuration correction, and other.
- **Application model**: Add an optional description. Application names are unique within the Organization and may be renamed without changing stable identity. Health is a read projection derived from Environment configuration, Assignments, and Assignment Convergence, not a stored lifecycle value.
- **Application workspace**: Use an Application header, Environment selector, and deep-linked views for Secrets, Draft and Publish, Bundle Revisions, and Assignment status. Environment and active view are route state. The default Environment is the most recently used still-authorized Environment or the first authorized Environment.
- **Environment protection**: Every new Environment is explicitly Standard or Protected. Existing Environments migrate to Unclassified and follow Protected rules until classified. Never infer classification from a name. Lowering protection requires the highest-risk confirmation path. Environment names are unique within an Application and can be renamed with impact-aware policy.
- **Activation Policy prerequisite**: An Environment can be authored without an Activation Policy, but cannot receive its first Assignment until one exists. The policy declares an ordered list of one to five constrained systemd units and one fixed `none`, `reload`, or `restart` post-Activation action. No arbitrary commands, per-unit actions, or per-Publish hooks are allowed.
- **Secret Value contract**: Management requests carry opaque Secret bytes as explicit base64 in JSON. Text input is UTF-8 encoded; file input preserves raw bytes. Core decodes and encrypts before persistence. The decoded maximum is 1 MiB, with matching Web preflight and Core request-body limits. Extend stable error codes with `payload_too_large` and any other new machine-readable identity or policy result; clients never parse message text.
- **Secret Value browser boundary**: Accept pasted text or one local file. Local filename is only an editable suggestion. Secret inputs are masked by default and shown only while a press-and-hold control is active. Clear bytes on blur, close, submission, and recovery. Never put Secret Values in Query cache, URLs, storage, logs, errors, analytics, snapshots, traces, or Audit Events. Do not implement Reveal.
- **Secret identity**: Secret names remain immutable and unique within their Application and Environment. File Binding validation retains relative POSIX path, safe ownership and mode, traversal, duplicate target, and reserved-name controls.
- **Secret authoring UI**: Create Secret and prepare Rotation in focused dialogs or panels. Draft is a dense table with a focused File Binding editor. Do not use one card per Secret or an inline value form in the list header.
- **Draft behavior**: Valid metadata and version-selection edits auto-save with optimistic concurrency. Show saving, saved, and conflict states. A stale ETag stops future saves and opens metadata-only comparison and explicit reapplication; never offer silent overwrite. Draft Reset restores selections from the current Desired Revision after a metadata-only preview and Audit Event.
- **Rotation behavior**: Prepare Rotation creates one immutable Secret Version and selects it in the Draft. It never automatically Publishes. UI and Audit language distinguish prepared Rotation from Rotation completed by Publish.
- **Publish behavior**: Reject empty and unchanged Drafts. Publish freezes a new immutable Bundle Revision and immediately advances the Secret Bundle's Desired Revision for all Assignments. Preview metadata-only changes, affected groups and nodes, existing failed/offline state, protection level, and Operation Reason. A successful request means Desired State updated, not all nodes deployed.
- **Rollback behavior**: Rollback copies an earlier Bundle Revision snapshot into a new immutable Bundle Revision and makes the new revision Desired State. It uses the same preview, Operation Reason, risk policy, Audit, and Assignment Convergence path as Publish.
- **Assignment identity**: Migrate Assignment from `(Node Group, Bundle Revision)` to `(Node Group, Secret Bundle)` and follow the Bundle's Desired Revision. Do not preserve fixed-revision or follow-latest modes in parallel. Publish and Rollback are the only first-release mechanisms that advance Desired State.
- **Assignment ambiguity**: A Managed Node may belong to several Node Groups but cannot receive more than one Assignment source for the same Application and Environment. Show conflicts before submission and enforce them transactionally for Assignment creation and membership changes.
- **Assignment entry points**: Environment Assignment status and global Fleet Assignment management use one shared workflow and policy. Environment context preselects its Secret Bundle; global Fleet supports cross-Application review.
- **Convergence schema**: Store Desired Revision, Observed Revision, latest Activation stage/outcome/error code, and timestamps for every Managed Node and Assignment pair. Preserve Activation reports needed for investigation. Existing single node-level observed revision becomes migration compatibility data and is not authoritative.
- **Managed Node state projection**: Core derives never-online, healthy, converging, failed, and offline. Default offline threshold is 75 seconds and is configurable by deployment policy. Primary-state priority is failed, offline, converging, healthy, then never-online, while secondary facts retain connection and Assignment context. A connected unassigned node is healthy plus unassigned, not failed.
- **Application and group health**: Aggregate from the underlying per-Assignment records and expose the contributing Environment, Assignment, and Managed Node facts. Use needs-attention, converging, healthy, and unconfigured for Application projection. No opaque backend status string without evidence is accepted.
- **Agent runtime inventory**: Heartbeats include Agent version, OS name/version, architecture, and hostname. Core combines these with certificate expiry, serial, enrollment time, and last seen. Do not model observed IP as stable Managed Node identity.
- **Fleet information architecture**: Nodes contains deep-linked Managed Nodes, Node Groups, and Assignments views. Managed Node detail contains Assignments and Convergence, activity, and node-information tabs. Node Group detail uses server-side search and selectable membership tables.
- **Batch operations**: The only first-release batch operation is adding or removing multiple Managed Nodes from a Node Group. Do not add generic selection controls to Applications or Assignments without a real action. Desired State-affecting removal follows the high-risk cleanup path.
- **Enrollment UI**: Register Managed Node is a focused flow launched from the node list. Install Command generation always requires Step-up Authentication. The command and Enrollment Token are displayed once, cleared on expiry or close, and never restored. Regeneration issues a new Token and Audit Event; the old command remains unrecoverable and follows its existing use/expiry state. Only Install Command has a sensitive copy affordance.
- **Unassignment state machine**: Unassignment and removal from an assigned Node Group create persistent per-node cleanup work. The Agent stops Activation Policy units in reverse order, removes the Materialized Bundle, and reports the result. The relationship remains removing until every affected reachable node confirms cleanup. Failed and offline results persist and are retryable.
- **Abandon Cleanup Confirmation**: An Administrator may stop waiting for unreachable nodes only through the strongest risk path. Core may remove the Desired State relationship but must retain `cleanup_unconfirmed` per Managed Node as a highest-priority attention condition. A reconnecting node processes cleanup before any new Desired State; failed cleanup blocks new delivery.
- **Structured Audit Event**: Replace free-form investigation fields with stable actor type/id/display snapshot, action code, resource type/id/display snapshot, outcome code, Operation Reason, correlation ID, occurred time, and redacted structured metadata. Keep events append-only and transactionally coupled to security-relevant state changes.
- **Audit UI**: Provide cursor-paginated filtering and detail for actor, action, resource, outcome, reason, correlation, and time. Link stable resource IDs to current detail while showing event-time names after renames. Do not add export or retention configuration in this scope.
- **Overview projection**: Add one read-only projection returning `generated_at`, compact asset/health summaries, risk-sorted attention items, recent Publish activity, and recent Audit Events. Attention items are derived current conditions, not Alert records, and cannot be acknowledged or dismissed.
- **Overview conditions**: Include identity/Step-up system errors where actionable, failed Assignment Convergence, offline nodes, Convergence pending beyond 30 seconds, Unclassified Environments, registered unassigned nodes, cleanup failures, and `cleanup_unconfirmed`. Exclude future Drift and Secret expiry until real signals exist.
- **Polling**: Overview and Convergence poll every 15 seconds; ordinary lists poll every 30 seconds. Pause when hidden, offline, or when refresh would disrupt active editing. Use bounded backoff after failures and always display last update time. Retain manual refresh.
- **Management pagination**: Atomically migrate growing v1 list endpoints from arrays to cursor envelopes with `items`, optional `next_cursor`, and optional `total`. Support `q`, structured filters, stable sort, and Core-bounded `limit`. No public external management client exists, so do not add v2 or dual response shapes.
- **Table pagination UI**: Use previous/next batches and 25/50/100 limits. Persist filters, sort, and limit in URL query parameters. Keep opaque cursor history in navigation state rather than public shareable filters. Do not implement arbitrary page jumps or infinite scroll.
- **Global search**: Search only Application name/ID, Environment name, Managed Node name/ID/serial, and Node Group name. Group results by type and enforce RBAC. Secret names and Audit Events remain in scoped search.
- **Error and stale state**: Core outage keeps timestamped cached content in read-only stale mode with a global banner. Disable mutations until health and identity recover. Overview's primary projection fails as a whole; secondary detail regions use feature boundaries and independent retry. Route and feature Error Boundaries catch unexpected render failures, while expected query and form failures stay local.
- **Mutation reliability**: High-risk and Desired State mutations do not automatically retry. Generate idempotency keys for retryable operations and reconcile uncertain outcomes by querying operation/resource state. Read requests may retry with bounded backoff.
- **Responsive tables**: Desktop uses stable columns and sticky headers. Tablet retains identity, primary state, key time, and actions; secondary fields move into expandable rows. Draft may use controlled horizontal scrolling. Mobile is read-focused and does not expose high-risk write workflows.
- **Theme persistence**: Store `light`, `dark`, or `system` browser preference locally and apply it before first paint. Do not add server-side theme settings or put theme in domain state.
- **Motion**: Limit functional transitions to approximately 150–200 ms and disable nonessential motion under reduced-motion preference. Keep refreshed table rows spatially stable and do not animate counts or stagger row entry.
- **Charts**: Do not add charts until a real historical data question and time-series contract exist. Use compact numeric summaries, status distribution, and attention lists for current state.
- **Capacity statement**: Keep the first-release backend claim and load evidence at 100 Managed Nodes, 100 Applications, and 10,000 active Secrets. Design frontend queries and list interaction so 1,000 Managed Nodes do not degrade, but do not advertise 1,000-node backend support without new capacity evidence.
- **Browser support**: Support the latest two stable versions of Chrome, Edge, Firefox, and Safari. Functional automation covers Chromium, Firefox, and WebKit; fixed-environment visual comparisons use Chromium.
- **Performance budgets**: Under fixed production-build CI throttling, representative routes target LCP no greater than 2.5 seconds, interaction response no greater than 200 ms, and CLS no greater than 0.1. Enforce route chunk budgets and test representative list interaction with 1,000 simulated rows.
- **Explicit lifecycle boundary**: Implement Rollback, Draft Reset, Assignment Unassignment, and assigned-group member cleanup. Do not expose UI placeholders for Retire/Purge, Reveal, Decommissioning, Emergency Revocation, Agent update management, Alert lifecycle, Drift, Secret expiry, Webhooks, Recovery Bundle operations, or legacy migration in this spec.

## Testing Decisions

- **What makes a good test**: Assert external behavior at the highest available seam: HTTP contracts, rendered and keyboard-accessible workflows, persisted domain results, Agent reports, and files/process outcomes. Do not assert component internals, SQL statement shape, Hook implementation, or private helper calls. Every security-sensitive happy path has denial, stale, timeout, concurrency, redaction, and recovery coverage.
- **Primary acceptance seam**: Extend the existing full-stack Playwright plus real Managed Node fixture against the running Core, PostgreSQL, management proxy, and Agent proxy. This is the primary proof for all four slices and should cover Bootstrap/MFA, member activation, shell navigation, Secret authoring, Publish, Rollback, Assignment, enrollment, per-Assignment Convergence, Audit investigation, Activation Policy, Unassignment, cleanup failure, and reconnect cleanup.
- **Management HTTP seam**: Extend the existing Go integration harness through `/api/v1` against a real PostgreSQL database. Validate every response against OpenAPI. Cover Session and Step-up expiry, RBAC, invitation consumption, last-Administrator protection, Environment classification, base64 and payload limits, cursor contracts, Assignment ambiguity, Publish/Rollback semantics, structured Audit Events, Overview projection, idempotency, and stale/uncertain mutation reconciliation.
- **Agent HTTP and lifecycle seam**: Extend the existing Python integration fixture through `/agent/v1` against a real test Core. Cover multi-Assignment desired envelopes, Activation reports by Assignment, runtime inventory, ordered systemd actions, failed action restoration, Unassignment task delivery, cleanup acknowledgement, offline recovery, cleanup-before-new-Desired-State, and `cleanup_unconfirmed` recovery.
- **Transactional invariant tests**: Use direct PostgreSQL-backed Core module/store tests only where HTTP tests cannot deterministically provoke the race. Prioritize single-use Bootstrap, Invitation and Recovery Codes; Draft ETag conflicts; last-active-Administrator protection; Assignment/membership ambiguity; Publish/Revision atomicity; structured Audit Event co-commit; idempotency; and Unassignment state transitions.
- **Pure projection tests**: Unit-test Managed Node primary state, Application health, attention-item risk ordering, Environment policy requirements, Operation Reason validation, cursor encoding/decoding, URL filter normalization, and metadata-only Revision diffs as pure functions where possible.
- **Web Hook and component seam**: Use Vitest, React Testing Library, user-event, and MSW for feature hooks and components. Cover explicit loading/empty/error/retry/success/stale states, keyboard focus, Auth routing, safe return targets, restricted Viewer controls, Step-up prompts, Secret Value clearing, press-and-hold reveal, Draft auto-save/conflict/reset, Publish and Rollback previews, cursor navigation, expandable tablet rows, and feature Error Boundaries.
- **Secret leakage tests**: Use unique canary bytes and assert absence from logs, error bodies, Audit Events, Query cache, browser storage, URLs, screenshots, traces, snapshots, and generated artifacts. Validate base64 decoding and the decoded 1 MiB boundary without checking real Secret content into source control.
- **Identity security tests**: Cover interrupted Bootstrap, pending-member denial, TOTP success/failure/replay window, one-use Recovery Codes, code-set regeneration, invitation expiry/revocation/replacement, account-and-source rate limiting, idle versus absolute Session expiry, background polling not extending idle time, multi-tab activity, renewal requiring MFA, password-change revocation, deactivated member denial, and host-local break-glass reenrollment.
- **Authorization tests**: Exercise every Administrator and Viewer route at the HTTP and browser seams. Assert hidden modules, explained disabled controls, server denial of direct Viewer mutations, Step-up-required codes, Grant expiry/revocation, and the server-side risk matrix for Standard, Protected, and Unclassified Environments.
- **Publish and Assignment tests**: Cover empty/no-change Publish denial, metadata-only preview, no-Assignment Publish, immediate Desired Revision advance, Rollback as a new Revision, multiple Node Groups with different Secret Bundles, same-Bundle overlap rejection, concurrent membership and Assignment races, and partial per-node Convergence without global success.
- **Unassignment tests**: Cover ordered stop and cleanup success, service-stop failure, cleanup failure after stop, offline nodes, retry, member-removal compound cleanup, Abandon Cleanup Confirmation, persistent `cleanup_unconfirmed`, reconnect cleanup before delivery, and rejection of new Assignment while cleanup remains unresolved.
- **Audit tests**: Validate stable codes, actor/resource snapshots, current-resource links, Operation Reason categories and lengths, optional external references, successful/rejected/business-failed high-risk events, anonymous abuse exclusion, redaction, immutability, cursor filters, and event order.
- **Visual regression seam**: Maintain deterministic fixtures for Auth, Overview, Draft, and Managed Nodes in 1440 and 1024 widths, light and dark themes, and representative loading, empty, error, stale, long-Chinese-copy, and populated states. Pixel comparison runs in fixed Chromium and font environments; baseline changes receive focused review.
- **Cross-browser seam**: Run critical functional E2E workflows in Chromium, Firefox, and WebKit. Edge support follows Chromium engine compatibility plus manual release smoke checks. Non-Chromium tests assert behavior, accessibility, focus, and no overflow rather than pixel identity.
- **Accessibility tests**: Combine automated accessibility checks with keyboard-only Playwright flows for login, MFA, navigation, filters, tables, dialogs, Secret forms, Publish/Rollback, registration, Node Group membership, and Unassignment. Verify focus trapping/restoration, accessible names, live status announcements, contrast, and non-color status semantics.
- **Performance tests**: Run production builds under fixed CPU and network throttling. Measure LCP, an INP-equivalent scripted interaction, and CLS on the four representative routes. Enforce route chunk budgets and flag long tasks while filtering, sorting, expanding, and selecting against 1,000-row fixtures.
- **Capacity tests**: Preserve the existing 100-Agent/100-Application/10,000-Secret release target and 30-second Desired State discovery target. Add query-plan and projection checks for Overview, cursor lists, structured Audit filters, and per-Assignment Convergence at that scale.
- **Prior art**: Reuse the repository's unified test entry point, unique-real-PostgreSQL test harness, kin-openapi response validation, generated TypeScript freshness checks, Python devproxy integration, envelope vectors, Vitest/RTL/MSW setup, and Playwright Managed Node fixture. Extend these seams instead of introducing repository-per-table abstractions or alternate client mocks.
- **Quality gates**: Every slice must pass formatting, lint, type checking, OpenAPI lint and generated-type freshness, Core tests and coverage gate, Agent tests, Web unit/component tests, production build, critical Playwright workflows, visual baselines, accessibility checks, `git diff --check`, secret scanning, and applicable dependency/container scanning.

## Out of Scope

- Persistent Alert acknowledgement, assignment, deduplication, suppression, resolution history, or notification delivery.
- Drift detection and restoration, Secret Version expiry, advance expiry warnings, and webhook delivery.
- Reveal of stored Secret Values.
- Secret Retire and Purge lifecycle.
- Managed Node Decommissioning and Emergency Revocation. `Abandon Cleanup Confirmation` applies only to Unassignment cleanup uncertainty and does not revoke node identity.
- Agent release approval, signed in-place update orchestration, or binary rollback UI.
- Recovery Bundle creation/restore UI and legacy age/TOML import or export.
- OIDC, passkeys, service accounts, public automation tokens, CI/CD write tokens, and per-Environment fine-grained RBAC beyond Administrator and Viewer.
- Canary, staged, scheduled, or per-Node-Group rollout selection. Publish immediately advances the one Desired Revision for every Assignment.
- Fixed-Revision Assignments or mixed fixed/follow-latest modes.
- Dynamic Node Group selectors, inherited Environments, shared Secret Versions, or multi-Organization tenancy.
- Kubernetes, Windows, macOS, container-native injection, environment-variable injection, templates, arbitrary file paths, arbitrary shell hooks, or inbound Agent control.
- Long-term time-series metrics and decorative dashboard charts.
- Audit Event export, retention-policy management, or SIEM-specific integration.
- Mobile support for complex or high-risk write workflows. Mobile remains authentication and read-focused.
- Backend capacity claims above the existing tested 100 Managed Nodes until new load evidence is produced.

## Further Notes

- This spec is the confirmed result of the operations-console grilling session. The design tree frontier is empty; remaining choices such as exact component tokens, query-key names, cursor encoding, schema column names, route slugs, and final logo geometry are implementation details governed by the decisions above.
- Domain vocabulary is defined in the root glossary. In particular, use Secret, Managed Node, Node Group, Assignment, Desired State, Bundle Revision, Assignment Convergence, Protected Environment, Operation Reason, Activation Policy, Unassignment Task, and Abandon Cleanup Confirmation exactly as defined there.
- ADR-0015 through ADR-0024 record the durable decisions behind per-Assignment Convergence, Environment protection, cursor pagination, Secret Bundle Assignment, Rollback history, structured Audit Events, bounded base64 Secret transport, Activation Policy and Unassignment, bounded MFA Sessions, and Organization Member lifecycle.
- This spec deliberately supersedes temporary first-slice assumptions that defer MFA and Step-up Authentication, pin Assignments to Bundle Revisions, store one observed revision per node, or limit Activation to files-only behavior. Those earlier specs remain historical records of the implemented MVP; they are not the target behavior for this effort.
- Existing trust decisions remain intact: management and Agent surfaces stay separate, Agents use outbound pull-only Convergence, node payloads remain encrypted and signed per Agent, PostgreSQL remains the Core database, and Audit Events remain append-only.
- The visual baseline is a gate, not a separate throwaway prototype. Auth, Overview, Draft, and Managed Nodes must demonstrate the selected system before remaining screens inherit it.
- Do not start by implementing every final page with mocked status. Each vertical slice must expose only behavior that Core and Agent can prove at that point.
