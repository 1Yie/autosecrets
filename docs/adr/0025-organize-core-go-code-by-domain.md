# Organize Core Go code by domain, not by layer

Core stays a single Go service (ADR-0001), but its business code is organized into three domain packages under `internal/` — `identity`, `secrets`, and `fleet` — each split into `handler.go` (HTTP parsing, validation, status codes) and `service.go` (business rules), with a `repository.go` that is backed by the shared `store` transaction handle rather than owning tables directly. Audit remains a cross-cutting package (`internal/audit`) that every domain records into and one handler queries; cross-domain calls happen through narrow injected interfaces (for example an `audit.Recorder`), not by importing another domain's concrete package. The near-empty `internal/server` package is deleted and its `AgentIdentityMiddleware`/`TrustedProxy` move to a shared HTTP package. Migration is incremental, starting with `identity` as the canonical sample domain while the remaining `app` package continues to serve until each domain is moved.

Rejected alternatives: a horizontal layer split (`internal/{handler,service,repository,model}`) would collide the ~twenty domain areas into single packages and blur boundaries as the code grows; per-domain repositories that own only their own tables would break cross-domain transactions such as Publish, which writes a Bundle Revision plus an Audit Event in one transaction; and a big-bang migration would break the HTTP-seam test suite (ADR-0001's "all product behavior is tested through these HTTP seams") without any behavioral gain.
